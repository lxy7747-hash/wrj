export interface PortParameters {
  txFrequency: Megahertz; txBandwidth: Megahertz; txPower: Watts
  rxFrequency: Megahertz; rxBandwidth: Megahertz; noiseFigureDb: Decibels
  transferRate: MegabitsPerSecond
  parameterSource?: LinkParameterSource   // D5
}
export interface DeviceParameters {
  /** 缺省的平台类型 / 端口按模板默认值补齐。 */

新增字段：

校验（`src/features/scenarios/scenario-validation.ts`，错误定位到字段路径）：
- 端口参数：频率、带宽、功率、速率必须大于 0，噪声系数不小于 0。天线增益必须是有限数。
- 链路端点必须存在对应端口（第 5.3 节）。不满足时报错，**激光链路除外**，激光保留配置、不写入脚本，界面不显示提示（2026-11-02 用户裁定 C-1）。
- D6：同一干扰平台类型下的干扰设备，频率、带宽、功率、探测距离、最小距离必须一致；每个干扰平台最多一台干扰设备。
- 盘旋：至少 2 个点，速度大于 0，只能用于上述三类平台。返航：`0 < timeS < duration`，至少 1 个点，速度大于 0。
- `detectionMinimumRange` 必须小于 `detectionRange`。

存储与导入：`server/local/scenario-sqlite.ts`、`src/features/scenarios/local-scene-import.ts`、`scenario-snapshot.ts` 要能保存和读取新增字段，缺省保持 undefined，由读取函数补默认值，不在存储层写入默认值。`parameterSource` 的保存校验参照 `server/scenarios/parameter-sources.ts` 的链路实现，扩展到端口参数。

### 5.4 实例（`comm_platform_INS.txt`）

2026-11-04 实例命名：生成时建立原 `platform.id` → 引擎实例名的映射，只修改生成副本，不迁移已保存场景。无人机与前出中继共用 `mission_uav_01` 起的连续序号；中继优先，同类按 `config.platforms` 顺序。两架中继占 01、02，作业无人机从 03 起；无中继时从 01 起。地面干扰站与机载干扰机分别从 `jammer_station_01`、`jammer_airborne_01` 编号，每次生成重新从 01 开始、至少两位补零。后方通信车、指挥车、天通、神通固定为 `rear_comm_vehicle`、`command_vehicle`、`tiantong_sat`、`shentong_sat`，同一卫星子类型最多一颗。

`mapping.json.platforms` 保存 `{ platformId: 原编号, name: 引擎实例名, generatedType }`；设备端点、业务、干扰、运动及 link_calc 引用均使用引擎实例名，`input.json` 保留原配置。实时位置优先按 `name` 映射回原编号；报告/回放按引擎日志及链路编号关联，不将 manifest 端点转回场景编号。

实例按模板顺序输出：后方车 → 指挥车 → 天通 → 神通 → 全局返航路线 → 无人机（含中继）→ 地面干扰站 → 机载干扰机。同类实例按配置顺序排列。

| 类型 | 写法（固定部分照抄模板） |
|---|---|
| 后方车 | `platform <id> REAR_COMM_PLATFORM`、`side blue`、`position`、`altitude`。有航点时追加 route |
| 指挥车 | `side blue`、`icon 737`、`position`、`altitude`、`heading 90 deg`。有航点时追加 route |
| 卫星 | `side blue`、`icon satellite`、`creation_time 0 sec`、`position 0n 120e altitude 35786 km heading 90 degrees`（固定，见 E3） |
| 无人机 / 中继 | `side blue`、`icon F-18`、`heading 90 deg`，**不写 position / altitude**。`route` 首点是初始位置，然后依次是航点；有盘旋时先写 `label LOITER`，再写盘旋点，最后 `goto LOITER`。有返航时写 `execute at_time <T> sec absolute`、`PLATFORM.FollowRoute("return_<id>");`、`end_execute` |
| 地面干扰站 | `side red`、`icon triangle`、`creation_time 0 sec`、`route position <初始位置> end_route`（有航点时追加）、`script_variables double detection_range_nm = <探测范围/1852>; end_script_variables` |
| 机载干扰机 | `side red`、`icon triangle`、`creation_time 0 sec`。route 首点为初始位置并带 `heading 0 deg`，接着是航点；有盘旋时写 `label orbit_loop`，盘旋点每点带 `turn left`，最后 `goto orbit_loop` |

- 全局返航路线：每个配置了返航的平台生成一个 `route return_<id>`，内容为返航点，放在无人机实例之前。模板中未被引用的 `relay_loiter`、`return_relay` 是示例内容，不生成。

### 5.5 link_calc（后方车，格式对齐模板）

字段顺序和写法：
```
  add processor link_calc WSF_LINK_CALC_PROCESSOR
    update_interval 5 sec
    emergency_threshold 1e-5
    warning_threshold   1e-6
    value_threshold_ber 1e-7
    jamming_range  30
    channel_encoding_scheme 0
    traffic_type            [...]
    relay_uav_names         [...]
    hot_link_ret            {...}
    hot_link_fw             {...}
    port_params             [...]
    natural_environment     {...}
    jammer_param            {...}
  end_processor
```
- **JSON 直接写，不再包双引号**。`jamming_range` 不带单位。去掉 `end_platform_type` 这一行。数值用 `String(value)` 输出（`1e-5`、`0`）。
- `port_params`：5 个通信平台类型，`comm_name` 用固定端口名，顺序与 5.2 节表格一致。transmitter 包含 `frequency_ghz`、`bandwidth_mhz`、`power_w`、`peak_gain_dB`、`information_rate_<单位>`；receiver 包含 `frequency_ghz`、`bandwidth_mhz`、`peak_gain_dB`、`information_rate_<单位>`、`noise_figure_dB`。单位键：无人机 / 后方车的卫通和微波用 `mbits/sec`；C/L 波段和光纤用 `bit/s`；天通用 `kbits/sec`；神通用 `mbits/sec`。光纤只写 `{"information_rate_bit/s":1000000000}`。**不写 polarization**。数值由端口参数和天线增益推导，所以和设备定义一致。
- `natural_environment` 的键和顺序与模板一致：sea_state 用 `mode`（不是 `model`）；`misc_loss_db` 只有两个键；去掉 `use_reflection_geometry`；`sea_polygon` 放在 `mode` 后面。`simplified_attenuation_db_per_km` 默认值按新模板改为 0.02。
- `jammer_param`：`weapon_name` 固定为 `prophet_jammer` 或 `alq99_jammer`，`platform_name` 用实例 ID，其余字段和顺序与模板一致。
- `hot_link_*`：沿用 `src/features/scenarios/hot-links.ts` 的链路链计算，跳点端口改用第 5.3 节的端口名。
- `relay_uav_names`：`FORWARD_RELAY_NODE` 实例 ID 列表，与无人机 `relayNames` 保持一致。

### 5.6 不再写入脚本（D1 保留项）

删除生成器中对应的代码：`EmitBusiness` 业务发送处理器、切换规则处理器、`forward_delay`/`return_delay`、中继 `relay_proc_*`、按设备生成的天线图 / 介质 / 网络、激光设备、侦测传感器、自动 / 定时干扰处理器、`global_environment`。`mapping.json` 和 `README.txt` 中列出“界面保留但不写入脚本”的参数和链路，供核对。

## 6. 本地运行兼容（P4，D4）

现有机制：`server/local/mission-runner.ts` 用 `engineHasLinkCalc` 探测引擎，引擎缺少该处理器时调用 `writeMissionPackage(..., stripLinkCalc=true)`，`server/local/script-file.ts` 的 `withoutLinkCalc` 去掉整段 link_calc。

本次扩展：**只在去掉 link_calc 的那个分支里**，在原位置注入一个补丁处理器 `local_link_stub`（生成器另外导出一个函数生成补丁文本，`script-file.ts` 替换时调用它）。补丁要做两件事：
1. **业务路由**：仿真开始时（`on_initialize2`，或 `execute at_time 0.001 sec absolute`），按热链和 traffic_type，对每个平台调用 `WsfSimulation.FindPlatform(name).SetAuxData(...)`，写入模板 script_proc 读取的 4 个键：`k<Type>_next_platform_name`、`_out_port_name`、`_next_in_port_name`、`_data_size`，多个值用 `|` 分隔。这样模板自带的 5 秒发送和 on_message 转发逻辑直接生效，不需要另写发送代码。
2. **干扰启停**：`execute at_interval_of 3 sec`，遍历 `jammer_param` 里启用的干扰设备，计算到蓝方平台的最近斜距。进入触发半径时 `TurnOn` 并 `SelectMode`（模式按干扰类型），**`trigger_radius_nm` 为 0 时不触发**；超出释放半径时先 `SelectMode("default")` 再 `TurnOff`。未启用的干扰设备在开始时 `TurnOff`（`alq99_jammer` 在模板中初始就是 `on`）。

保存给对接方的 TXT、脚本预览、`writeScriptText` 都不包含补丁。引擎有 link_calc 时原样运行，也不注入补丁。

- 现在干扰设备的“干扰范围”（`Jammer.jammingRange`，对应 `trigger_radius_nm`）限制在 1～100 km，生成器要求大于 0（`mission-generator.ts` 中 `jammingRange > 0` 的检查，`scenario-validation.ts` 中 `JAMMER_RANGE_METERS` 的写入校验，`JammerEditorDialog.vue` 的“干扰范围（km，1～100）”）。改为**允许 0**，范围 0～100 km，0 的含义是“不触发”，在控件旁说明。
