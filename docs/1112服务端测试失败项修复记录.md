## 1. `tests/server/no-side-effects.spec.ts`

### 复现

```text
server/admin/projection.ts：readsSystemDate 返回 true
后续同一用例在 host/storage/process modules 检查中发现 server/http/loopback.ts 导入 node:net
```

### 根因

1. `server/admin/projection.ts` 在以下 4 处直接读取系统时间：
   - `capturePublishedParameterSources` 的发布引用 `createdAt`
   - `recordEquipmentVerification` 的 `verifiedAt`
   - `recreateEquipment` 的 `occurredAt`
   - `deleteEquipment` 的 `occurredAt`
2. 修复 Date 后，同一用例继续发现 `server/http/loopback.ts` 从 `node:net` 导入 `isIPv4`。该文件在生产运行时闭包内，违反 P0 无宿主副作用边界。

这两处都来自工作区既有未提交改动，但与无副作用约束冲突，属于实现问题。

### 修复

- `server/admin/projection.ts`
  - 新增 `AdminClock { now(): string }` 与 `DEFAULT_ADMIN_NOW = '2026-08-06T08:00:00Z'`。
  - `AdminProjection` 增加第 5 个可选构造参数 `clock`，默认固定时钟；4 处时间统一使用 `this.now()`。
  - 生产入口 `server/app.ts` 在存在 `authStorage` 时注入 `{ now: () => authStorage.time() }`，纯 Mock 使用固定时钟。
- `server/http/loopback.ts`
  - 移除 `node:net` 导入，改为本地严格 IPv4 点分十进制校验（拒绝前导零、越界段）。
  - 未改变部署入口、回环判断、Origin/Host 校验行为。
- `server/local/equipment-sqlite.ts`、`server/local.ts`
  - 为装备 SQLite 存储注入同一时钟；生命周期 DELETE/RECREATE、旧库升级标记和发布引用兜底时间
    与 `AdminProjection` 使用同一时刻，避免 SQLite 分支仍回落到系统时间。
  - 未改变数据库结构、接口或已有记录。
- 新增 `tests/server/admin-clock.spec.ts`：
  - 注入固定时钟后核验、发布引用、删除、重建事件均为同一时刻；
  - 纯 Mock 默认使用公开固定时刻。

### 影响

管理投影的时间字段不再来自系统时钟，而是统一来自注入时钟；真实账号库入口仍与 `authStorage.time()` 保持一致，API 字段和业务行为不变。

## 2～4. `tests/server/real-data-smoke.spec.ts` 三项失败

### 数据来源

```text

AFSIM_POSITION_LOG_PATH=H:/Project/newWrj/output/position.csv
```

原始数据统计：

```text

平台：rear_comm_vehicle、command_vehicle、tiantong_sat、shentong_sat、
      mission_uav_01、mission_uav_02、mission_uav_03、jammer_station_01

MESSAGE_TRANSMITTED：14044
MESSAGE_RECEIVED：14044

```

旧断言对应的参考样例在：

```text
H:/Project/newWrj/frontend/output/local-deployment/input/scenario_events.csv
```

该文件统计：

```text

MESSAGE_TRANSMITTED：5155 / MESSAGE_RECEIVED：5105

配对的链路：17，歧义 0，卫星中继窗口与直连中断均符合旧断言
```

结论：旧断言不是跨版本不变量，而是针对 9 平台参考样例写死的场景事实；`.env.local` 当前指向另一份 8 平台、1112 自定义消息类型的运行数据。数据文件本身没有损坏，解析器也未丢行。

### 2. `WEAPON_TURNED_ON` 数量为 0

- 当前原始 CSV 只有 `! WEAPON_TURNED_ON, ...` 字段声明，没有该事件的数据行。
- 解析结果 `weaponEvents.length === 0` 与原始数据行数一致，不是解析遗漏。
- 旧断言 `toBeGreaterThan(0)` 对当前样例不成立。

修复：

- 真实数据用例改为先统计原始数据行，再断言 `解析条数 === 原始行数`：
  - 有该事件时继续校验错位声明下的 lat/lon/alt；
  - 没有该事件时断言 0，不把“样例没有”当成解析通过。
- 新增确定性 CSV 用例，显式构造带扩展列的 `WEAPON_TURNED_ON`，验证 lat/lon/alt 与 `csvExtraColumns` 保留。

### 3. `ambiguous=10750`

- 当前数据是多跳中继场景：同一消息序号在 0.15 秒窗口内会同时出现上一跳和下一跳的发送记录。
- 原配对逻辑把所有候选都视为来源。例如接收 `command_vehicle fiber_link` 时，候选同时包含：
  - `rear_comm_vehicle fiber_link`（有效光纤来源）
  - `command_vehicle c_band_uplink`（下一跳数传，无法与接收端构成已知链路）
- 修复：先按设备类型/端口过滤出能构成已知链路制式的候选；只有兼容候选全部为空时才回退到原候选集合，继续计入 `unclassified`，不静默丢弃。
- 效果：当前数据 `ambiguous` 由 10750 降到 3060。
- 剩余 3060 条均为同制式多跳候选：

```text
1530 kForwardSituation：mission_uav_01 microwave_link + rear_comm_vehicle microwave_link
1530 kForwardTarget：   mission_uav_01 microwave_link + rear_comm_vehicle microwave_link
```

仅凭消息序号、类型和时延无法唯一确定来源，继续如实计为歧义，不猜来源、不清零。

同时补齐 1112 模板消息类型的方向判定：

```text
FORWARD：kForwardSituation、kForwardTarget
REVERSE：kReturnReconVideo、kReturnReconStatus
```

真实数据用例改为验证：
- 所有接收记录都有明确归类；
- 链路端点、非自环、条数、类型、方向自洽；
- 活跃区间首末与投递时刻一致；
- 有卫星链路时校验 GEO 时延；不再假设固定的卫星干扰窗口和固定直连中断次数。

### 4. `PLATFORM_ADDED` 数量 8 对 9

- 当前原始数据只有 8 条 `PLATFORM_ADDED` 数据行。
- 缺少的平台是 `jammer_airborne_01`；不是解析去重或合并导致。
- 当前平台声明与快照节点完全一致；红方只有 `jammer_station_01`。
- 旧断言 `toBe(9)`、固定 7 蓝 2 红是参考样例事实。

修复：
- 平台数量改为由 `PLATFORM_ADDED` 数据本身决定；
- 断言 `节点数 === 声明数`，节点阵营逐项匹配声明；
- 断言红方恰好等于类型包含 `JAMMER` 的平台，蓝方数量由总数推导；
- 不再硬编码 9 / 7 / 2。
